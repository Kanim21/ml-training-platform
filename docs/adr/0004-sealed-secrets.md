# ADR 0004: Sealed Secrets for credentials in Git

**Status:** Accepted

## Context

The blueprint forbids plaintext secrets in Git and allows either Sealed
Secrets or External Secrets. The lab has no cloud account and no Vault, so
there is no external secret store to sync from.

## Decision

- Run the Sealed Secrets controller (pinned upstream release manifest, in
  `kube-system` under kubeseal's default name). Credentials live in Git as
  `*.sealed.yaml`, encrypted to the controller's public key.
- Generate credentials rather than typing them: `scripts/seal-s3-credentials.sh`
  creates a random S3 key pair and pipes it straight into `kubeseal`, so the
  plaintext never touches disk.
- Where a component can generate its own credential in-cluster, let it. The
  Postgres password is generated by CloudNativePG into the `mlflow-db-app`
  Secret and never exists in Git in any form.
- The controller app has prune disabled; deleting it would orphan the sealing
  key.

## Consequences

- **The sealing key is now state that needs a backup.** A rebuilt cluster
  generates a new key and cannot decrypt the committed SealedSecrets. Before
  the full-rebuild drill (6), either back up the key
  (`kubectl -n kube-system get secret -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml`,
  stored outside Git) and restore it before ArgoCD syncs, or re-run
  `scripts/seal-s3-credentials.sh` and commit. This is not automated yet.
- SealedSecrets are scoped to name and namespace, so the same S3 key pair is
  sealed once per namespace that consumes it.

## Alternatives considered

- **External Secrets Operator.** It needs a backing store (Vault, a cloud
  secret manager). Running Vault just for this would add more than it proves.
  It's the better fit for the optional EKS phase, with AWS Secrets Manager.
- **SOPS with age.** It works with ArgoCD only through a plugin or
  KSOPS-patched repo-server, which means more moving parts in the GitOps path.
